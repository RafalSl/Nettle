# Work plan: changes after the first real use (2026-11-23)

What gets built from `docs/reviews/2026-11-23-first-use-review.md`, with the user's decisions of 2026-11-23 (requirements v0.9.8). This is build-plan Phase 4, tasks 19 to 28, in detail. Nothing here is built yet.

## How every task runs

- One branch per task, `feature/<name>` cut from `develop`; merged back into `develop` once `./run.sh npm run check` passes (typecheck, lint, format, tests). PR #1 (the review and these docs) is merged into `develop` first.
- **Data changes (NF-8).** A task that changes stored data ships, in the same branch:
  - an append-only SQLite step, plus a test that builds a database at the previous version with synthetic rows, runs `migrate()` and checks the rows;
  - a preferences upgrade step, if the preferences change, with a test from the previous version;
  - an export `schema_version` bump, if the export shape changes, with a test that imports a file of every earlier version.
- **Before the phone gets a branch that migrates** (tasks 19, 20, 21, 24, 27): export a Full backup first. The database copy from task 19 is a second net, not a replacement.
- Each task ends with: requirement status updated (drop "v0.9.8 change not built"), a work-log entry, and new or changed checks in `docs/phone-test-plan.md`.
- Requirement IDs go in commit messages and test names.

Sizes: S is about one session, M two, L three or more.

## 19. migration-safety (NF-8)

**Goal:** the tools every later task needs to change data safely.

- **Database copy before migrating.** `migrate(db, { backup })` gets an optional callback that runs once, before the first pending step, only when the database already has a version (not on a fresh install). The expo adapter implements it with `VACUUM INTO '<documents>/SQLite/nettle-before-migration.db'`, deleting the old copy first so only the latest is kept. `VACUUM INTO` is plain SQL, so it goes through the `SqlDb` seam and is tested on `node:sqlite` (like `pg_dump` run from inside the connection). It cannot run inside a transaction, so it runs before the step loop. Verify against the Expo SDK 58 docs: the database directory (`SQLite.defaultDatabaseDirectory`) and that the bundled SQLite supports `VACUUM INTO` (3.27 or newer).
- **Delete data removes the copy** (it holds the same health data): the Delete data use case (SE-9) calls a new adapter method behind the storage port; "everything" deletes it, and a group delete deletes it too, so a deleted group cannot come back from the copy.
- **Migration steps in code.** `MIGRATIONS` becomes `(string | ((db: SqlDb) => Promise<void>))[]`, so a step that moves data (task 21's backfill) can be written in TypeScript and still runs in the step's transaction.
- **Preferences version.** `Preferences.version` (current shape = 1; stored JSON without it is 1). `core/model/preferencesUpgrade.ts`: a list of pure steps `(json) => json` and `upgradePreferences(json)`, used by `sqliteRepo.getPreferences` (replacing the default-filling spread, which stays as the last step), by the in-memory fake, and by `parsePreferences` on import. No step yet; tasks 24 and 27 add the first.
- **Export reader by version.** `core/export/upgrade.ts`: `upgradeDataJson(raw)` runs steps from `raw.schema_version` up to `SCHEMA_VERSION` before `parseDataJson` validates. Still version 1 here; tasks 20 and 21 add steps.
- **Tests:** the copy is made once when steps are pending, not on a fresh database, not when nothing is pending, and the old copy is replaced; a TypeScript step rolls back with its transaction; preferences without a version read as 1; `upgradeDataJson` leaves a current file unchanged; Delete data removes the copy (contract test on both stores).
- **Docs:** NF-8 status; README line "export a Full backup before installing a branch that migrates".
- **Phone:** start the app on an existing diary: it opens normally; the copy can only be seen through a later restore, so the check is "no change in behaviour".

## 21. skin-check (SK-3, SK-8, EN-1, EX-1, UX-2)

Three commits on one branch: 21a data and core, 21b the stepper, 21c the rest of the app.

### 21a. Data and core
- **Data:** `skin_entry.check_id TEXT` and `nail_entry.check_id TEXT` (a column added to a table with rows cannot be `NOT NULL` without a default in SQLite, so: add the column, backfill, then every write path sets it; the type in TypeScript is non-null) with an index each.
- **Backfill (decided: group).** A pure function in `core/model/checks.ts`, `groupIntoChecks(entries)`: entries (skin and nail together) sorted by time; a check starts at an entry and takes each later entry that is within 15 minutes of the check's first entry and belongs to an area not yet in the check; the check id is the id of its first entry; each entry keeps its own time. The migration step (TypeScript, task 19) reads both tables, calls it and writes the ids. Same function in the export 2→3 step, so an old backup imports grouped the same way.
- **Model:** `SkinEntry.checkId`, `NailEntry.checkId`; `SkinCheck` (a read model, not stored): `{ id, at, entries }`, with the check's time = its earliest entry's.
- **Storage port:** `putRecords(batch)` writes several records of several kinds in one transaction (both stores, contract test), so a check is saved whole or not at all.
- **Use cases** (`core/usecases/skinCheck.ts`):
  - `checkDraft(deps)`: the active areas in order with each one's last values, last time and whether it has an earlier entry.
  - `saveSkinCheck(deps, { at, steps })`: validates every step like `logSkinEntry` and `logNailEntry` do, gives all entries one new check id and the same time, writes them with `putRecords`; refuses a check with no logged area. Photos are attached afterwards per area entry (SK-4), as now.
  - `noChangeForAll(draft)`: pure; marks every area that has an earlier entry.
  - `getCheck(deps, id)`, `editSkinCheck(deps, id, { at, steps })` (keeps ids of kept entries, adds entries for areas added, deletes with tombstones the ones removed, moves every entry to the new time when the time changes), `previewCheckDelete`, `deleteSkinCheck` (one `deleteWithTombstones` call for all entries and their photos).
  - `repeatAllAreas` now saves one check (it is the same thing as "No change for all" plus Save).
  - The Nails form saves a check of the nail areas it logs.
- **Export:** `check_id` on `skin_entries` and on the nail entries codec; `schema_version` 3; the 2→3 step uses `groupIntoChecks`.
- **Tests:** `groupIntoChecks` (15-minute edge, same area twice → two checks, skin and nail together, the id is the first entry's); migration of a database with synthetic loose entries; `saveSkinCheck` (one id, one time, all or nothing when one step is invalid, archived area refused); edit (add, remove, time change); delete (tombstones for every entry, photos go too); import of version 1 and 2 files; merge of a file whose entries already have check ids.

### 21b. The stepper
- `forms/skin/SkinCheckForm.tsx` replaces `SkinForm` at `/form/skin`; it also takes `?check=<id>` for editing. State in a `useSkinCheckDraft` hook (like `useMealDraft`): current step, per-area values, per-area state (pending, changed, same, skipped), pending photos per area.
- **Title:** a new `ui/useScreenTitle.ts` sets the header title from the screen (`navigation.setOptions`) and re-runs when the language or the step changes: "Skin · Neck 2/8". Task 28 applies the hook everywhere.
- **Area strip:** a horizontal scroll of chips with a state mark, scrolling itself to the current chip; a tap jumps.
- **Step body:** large area name, "Last: yesterday 21:40 · severity 6" (or "First entry for this area"), then `SkinScoreFields` or the nail fields, `PendingPhotos`, the note.
- **Areas in flare (SK-6):** `checkDraft` also returns each area's open flare, if any (from the existing flare derivation, with the area's own threshold). Such an area has the coral severity badge on its strip chip and on its step, and Skip reads "Skip (flare stays open since 12 Nov)", so it is clear that only No change or new scores record that the flare goes on. No data change.
- **Floating bar** (in place of `FloatingSave` until the summary): No change, Skip, Next. On the summary it becomes Save.
- **Summary:** `ui/ScoreTable.tsx` (also used in task 25) with a state column, the time field, "Not logged: …" with "No change for these", and "No change for all areas" as the first button of step 1.
- **Cracks and size (review section 14, waiting for approval):** no Details button; one card with the cracks switch and a "Patch size" row with − and +, Set, and × to clear (tap the number to type). `SkinExtraFields` is rewritten for this, and the edit form uses it too.
- Discard Changes on dismiss when any step was touched (UX-3); `missing` blocks Save while an invalid size is entered or nothing is logged.
- i18n: `skinCheck.*` keys in English and Polish (Polish as a draft).
- **Tests (screen):** walk three areas (change, no change, skip) and save → one check with two entries; jump by chip; "No change for all" then Save; an area without an earlier entry has no No change; an area in flare shows the badge and the Skip wording, and loses both once its severity is below its threshold; the title shows area and step in both languages; invalid size blocks Save; edit mode removes and adds an area.
