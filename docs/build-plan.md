# Build plan: Aurora ring design

Status: built 2026-11-21 (all 16 tasks merged into `develop`); the phone run is still to do. Deviations are in the work log: gestures use `PanResponder` and motion uses React Native's `Animated` instead of gesture-handler and reanimated; the confirmations and action sheets stay native iOS sheets; the missing states were built only where a pattern fit. Design: `docs/design-system.md` (approved parts and the "Proposed additions" list), boards in `design/canvas/`, review in `design/consistency-report.md`. Rules in CLAUDE.md apply to every task: one `feature/<name>` branch per task cut from `develop`, `npm run check` passing, a work-log entry, requirement IDs in commits, merge into `develop` when the checks pass, never into `main`. The prototyping decision holds: no migrations or old-data handling; a plain new SQL step is fine.

Phase 1 builds the approved design. Phase 2 builds the "Proposed additions" (boards `G1-` to `G6-`) and starts when phase 1 is done.

## Phase 1: the approved design

## Phase 2: proposed additions

Assumption (the user's, 2026-11-21): the proposals need few or no changes. Before starting, re-read `design-system.md` and the canvas for remarks the user made in the meantime. Anything unchanged is built as drawn. Where a proposal changes a requirement, the same branch updates `requirements.md` (with its Changelog entry), `ux-design.md` and `user-flows.md`, and removes the proposal from "Proposed additions". ## Phase 3: changes after the first review (2026-11-21)

Both come from the user after looking at the finished boards. Branch per task, as in the phases above.

17. **language-setting** (UX-6, UX-7, NF-6, LL-11, EX-3; board `G7-Language`).
   - Core, with tests, no Expo imports: a `Language` preference, `'system' | 'en' | 'pl'`, default `'system'`, stored with the other preferences so the export's settings part carries it (EX-1; `schema_version` stays 1 and, in the prototyping phase, a plain SQL step is enough if the preferences table needs a column). A pure `resolveLanguage(preference, deviceLanguageCode)` that gives `'pl'` for `'pl'`, or for `'system'` when the device language is Polish, and `'en'` otherwise.
   - i18n adapter: `setLanguage(preference)` sets `i18n.locale` from `resolveLanguage` and the device locale (`getLocales()` today sets it once at start-up). `currentLanguage()` (LL-11), `dayParts` and the report's default (EX-3) already read `i18n.locale`, so they follow without other changes. Reminders already scheduled keep their old text, so reschedule them after a change (SK-9, IN-17). Ports and adapters: the preference lives behind the existing settings storage port; the screen only calls a use case.
   - UI: a `LanguageSettings` page in `settingsPages.tsx` with three single-choice rows and the "What changes" list, and the Language row, value "Device (English)", first in the About group of `SettingsScreen`. New keys under `settings.language*` in `en.json` and `pl.json`. Re-render: the language lives in the composition root (`services.tsx`) and the navigation root is keyed by it, so every screen remounts in the new language; this closes nothing the user has open, because the setting is only reachable from Settings.
   - Tests: `resolveLanguage` cases (device Polish, device English, device other, explicit choices); the i18n switch changes `t()` and `currentLanguage()`; the screens test renders the About group with the row; the export and import contract carries the preference.
   - Docs in the same branch: requirements statuses of UX-6, UX-7, NF-6 and LL-11 to Done (drop "v0.9.5 change not built"), and a step in `phone-test-plan.md` (S5: choose Polski and English from the setting, with the device set to the other language). The phone run: Expo Go takes its language from the device, so the explicit choices are the real test.
18. **app-icon-nettle** (UX-12; boards `G7-AppIcon-Nettle`, `G7-Splash-Nettle`). The user chose option A on 2026-11-21: one serrated nettle leaf inside the ring (B and C stay on the canvas for the record). `design/generator/appicon.py` draws the leaf with the same shape as `leaf_path` in `design/generator/group7.py` and rewrites `icon.png`, `splash-icon.png`, `favicon.png` and the three Android layers (the monochrome layer is the leaf and the ring in one colour). Check the PNGs by opening them, at 1024, 180, 60 and 29 pt; Expo Go always shows its own icon, so the icon is only seen in a standalone build. The boards `G6-AppIcon` and `G6-Splash` are the first version and can be deleted. Add the icon and splash checks to `phone-test-plan.md` (S6, done 2026-11-21).
