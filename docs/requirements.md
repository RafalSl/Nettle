# Food Allergy & Skin Condition Diary: Requirements v0.9.4

Nov 21, 2026 · @Rafal

## Overview and goals

A private iPhone diary where one person logs what they eat and take and how their skin and health feel, so patterns can be reviewed with a doctor. All data stays on the device.

- **Problem:** recurring scaling, itchy and sometimes painful skin patches with no confirmed diagnosis. Doctors recommended a diary to find out whether food or other triggers are involved.
- **User:** a single person, on their own iPhone. The app is never distributed.
- **Done means:** daily logging takes about a minute, the full log exports as a doctor-ready bundle, and an on-demand LLM analysis suggests possible patterns.
- **Not a goal:** diagnosis or medical advice. LLM output is always presented as tentative hypotheses.

Status used below: **Done** (built and tested; phone checks are in `docs/open-questions.md`), **Not built** (EX-12 and UX-8 are Later; UX-8 is not planned until the user says so), **Bug** (built, but it does not behave as written; the bug is listed in `docs/open-questions.md`). Update the column when a task finishes.

Priorities used below: **Must** (v1), **Should** (v1 if cheap), **Later** (after v1).

## Intake logging

Every entry has a timestamp (editable, so past meals can be added) and an optional note. Reactions can lag a trigger by a day or more, so exact times matter.

## Skin and health logging

Skin status is logged per body area, with several separate scores, so the analysis can tell itching from scaling and a flare from a calm day. Nails are their own kind of area, and Daily health holds everything that is recorded once a day.

| ID | Requirement | Priority | Status |
| --- | --- | --- | --- |
| SK-1 | Predefined skin areas: chin, neck, ears (inside), behind the ears, sternum, penis, perineum and groin, between the buttocks. The last three replace the single "intimate area", because they respond differently to treatment, and are sensitive by default (SK-5). Other places (a spot on a knee, the palms) are user areas (SK-2) | Must | Done |
| SK-2 | The user can add, rename and archive areas. Predefined areas keep a stable id and show a localized name; renaming one stores a `name_override` that takes precedence until cleared. Active area names are unique, compared without regard to case | Must | Done |
| SK-3 | Per skin area and entry, separate 0–10 scores for severity, itch, pain, dryness and scaling. A new entry is prefilled with the area's last values, and "no change" saves it in one tap, for skin and nail entries alike. "No change for all areas" saves every area in two taps. Scores are set with a slider and − and + buttons for single steps (UX-3). A skin entry also has a "cracks or open wounds" yes/no and an optional size in mm (the largest diameter), meant for an area that is one fixed patch; both are prefilled and carried by "no change" like the scores, and the size stays empty until the user sets it. Both are exported (EX-1), shown on the timeline (SK-8) and in the report (EX-3) and given to the analysis (LL-2) | Must | Done |
| SK-4 | Dated photos attached to an area entry, several per entry, so a doctor can review how an area changed. Photos are added in the Skin and Nails forms before saving and later from the entry's edit screen; a photo can be the only change (scores unchanged, plus a photo). For every photo the app derives the time since the last treatment application on that area (IN-11): the treatment's name and the elapsed time, or "no treatment logged" within the last 7 days. The program computes it from the timestamps, not the LLM, so it is exact and repeatable; it is shown with the photo on the timeline (SK-8), printed in the photo captions of the report (EX-3) and given to the analysis whenever photos or their entries are (LL-2). Nothing is stored: it is recomputed when applications are added, edited or deleted | Must | Done |
| SK-5 | Each photo has a sensitive flag; areas can be sensitive by default (penis, perineum and groin, and between the buttocks are) and the user can override per photo | Must | Done |
| SK-6 | Flares are derived, not logged: a flare is a period in which a skin area's severity (SK-3) is at or above a threshold (default 8, set in Settings, Logging). It starts at the first entry at or above the threshold and ends at the first later entry below it; overlapping periods of different areas are merged into one body-wide period that lists its areas, and a period with no later entry reads "open at last entry". Timing is only as precise as the logging. Editing a severity or changing the threshold recomputes the flares from the entries. Nail areas have no flares | Must | Done |
| SK-7 | Daily health (formerly the daily check-in): one screen and one record per local day, made of check-in items. An item is either a 0–10 score or a yes/no. The predefined items are wellbeing, stress, sleep quality and abdominal pain (scores), bloating (yes/no) and the daily tags (IN-6, yes/no); each has a stable id and a short description. The user adds, renames and archives items; an archived item is no longer asked but stays in the history, the report and the analysis. The record also holds a free-text note. Stool entries stay separate (Bristol type 1–7, timestamped, several per day). Daily health offers an explicit "same as yesterday" for all items; values are never filled in silently, and an item the user has switched off or archived in Settings is not asked or recorded. Saving the record logs the day (SK-11) | Must | Done |
| SK-8 | Timeline view per area showing scores and photos side by side across dates. A date picker jumps to a date: the timeline scrolls to that day, or to the nearest earlier day that has an entry, and says so. A tap on an entry opens the same Edit and Delete sheet as the day's log (EN-1) | Should | Done |
| SK-9 | Reminders as local notifications: a daily one for Daily health, sent only while the day has no Daily health record (saving one reschedules it), a weekly one to photograph nails while nail areas exist, a monthly one to export, and per-item reminders for regular medication and treatment (IN-17). Tapping a reminder opens its target: the Daily health form for the day the reminder was delivered, the nail update form, the Full backup screen (EX-14) or the quick sheet of regular items. It does nothing while a form has unsaved changes and is handled once per reminder. Reminder texts never contain entries; a medication reminder shows the item's name unless the user hides it (IN-17) | Should | Done |
| SK-10 | Nail areas: every area has a kind, skin or nail. The user adds one nail area per affected nail. A nail entry has a stage (red or dark edge, separation, yellow, white, clear), a rough extent (none, under a quarter, up to half, more than half) and photos (SK-4, SK-5), instead of the five scores | Must | Done |
| SK-11 | Day logged: saving the Daily health record (SK-7) marks that local day as fully logged for meals and other intake; there is no separate switch. Saving a day with no meals logged asks for confirmation first. A day without a Daily health record counts as not fully logged in the analysis and the report (LL-4); deleting the record makes the day unlogged again | Must | Done |
| SK-12 | Time to relapse, derived and not logged: for each skin area and treatment, a course is a run of applications on that area with no gap longer than 7 days, so that maintenance use twice a week counts as one course; the cost is that two real courses less than a week apart merge into one. For each finished course the app computes the days from its last application to the start of the next flare of that area (SK-6), or "no flare yet". One pure function computes it from the entries, with the gap as a constant; it is recomputed when entries or the flare threshold change. Timing is only as precise as the logging, and a different treatment applied in between is listed beside the result as a confounder. Shown in the report (EX-3) and given to the analysis (LL-2) | Should | Done |

Photos are stored on the device, in the app's private storage, and never leave it except through an export or an LLM run the user explicitly confirms.

## Editing and deleting entries

Until now only bulk delete (SE-9) existed, so one wrong entry could not be corrected.

| ID | Requirement | Priority | Status |
| --- | --- | --- | --- |
| EN-1 | Any single entry can be opened from the day's log (Today or Review), and a skin or nail entry also from its area's timeline (SK-8), then edited and deleted; both places use the same action sheet. Editing keeps the entry id and the rules of creating: a reaction cannot be before its meal, and a day has one Daily health record. Flares are never edited or deleted on their own: they follow the skin entries (SK-6). Deleting asks for confirmation in an action sheet that names what goes with the entry (a meal's reactions, an entry's photos) and leaves a tombstone (EX-13). Areas, treatments and tags that entries use are archived, not deleted | Must | Done |

## LLM features

The LLM is the Anthropic API, paid per use through a Console account. A Claude Pro subscription does not cover API calls. The app calls the API directly from the phone; no backend is assumed.

| ID | Requirement | Priority | Status |
| --- | --- | --- | --- |
| LL-1 | Photo to ingredients: send a meal photo, get an ingredient estimate back, shown for review (see IN-3) | Must | Done |
| LL-2 | On-demand pattern analysis over a user-chosen date range, over all record types: intake, allergen tags, treatments, change events, Daily health records, stool, skin and nail entries, and the derived flare periods (SK-6). It asks for the order and lag between flare start, digestive changes and nail changes. It is also given the reactions to treatment applications (IN-11), cracks and sizes (SK-3), medical events (IN-18), the time to relapse per area and treatment (SK-12) and, for photos, the time since the last application (SK-4); the last two are computed by the program and passed as numbers, not left to the model | Must | Done |
| LL-3 | Analysis windows: same day, 24 h, 48 h and 72 h after intake, not only the previous meal; plus 7-day and 21-day lookbacks for illness, antibiotics, stress, sleep and change events | Must | Done |
| LL-4 | The prompt asks for tentative hypotheses with stated uncertainty and the data behind each one, never conclusions. It treats treatments as confounders, counts and discounts days without a Daily health record (SK-11), and says so when the data cannot answer a question, for example for a food eaten on most days. It is told where each ingredient list came from (IN-16) and treats photo estimates as rough and name estimates (IN-19) as rougher still, because they are a typical recipe and not what was eaten | Must | Done |

| LL-6 | Photos are excluded from analysis by default; the user opts in per run and selects some or all, sensitive photos included only by explicit choice | Must | Done |
| LL-7 | Each analysis is stored as its own object: date range, model, run date, prompt version, result. Raw entries are never modified | Must | Done |
| LL-8 | Failures (no network, invalid key, rate limit, spend cap reached) show a clear message and lose no data | Must | Done |
| LL-9 | The model is a setting for each LLM action (label scan, meal photo, meal name, analysis, report summary; any later action gets its own), not hard-coded. | LL-10 | LLM provider abstraction: one interface for reading ingredients from an image (meal photo and label scan) and one for analysis, with a separate adapter per provider (Anthropic first). | LL-11 | LLM output language follows the app language, which is the device language (English or Polish; UX-7) | Should | Done |

| LL-13 | Label to ingredients: send a label photo, get the ingredient list, allergens and "may contain" traces back as structured JSON, shown for review (see IN-15). Date ranges are chosen as diary days (NF-7) and converted to UTC bounds using the device's current timezone at export time (inclusive at both ends). A later setting may change this.

The API key is never included in any export. The export screen warns that photos may be sensitive, and that a forgotten ZIP password cannot be recovered. In an encrypted ZIP the file names, sizes and dates stay readable (a limitation of the ZIP format), so photo file names must not reveal more than necessary, and the password key derivation is weak by design (1000 PBKDF2 rounds), so the export screen asks for a long passphrase.

**Accepted risks:** anyone who controls the device or its certificate trust settings can see the key in network traffic while it is in use, since Keychain protects the key at rest only. A jailbroken or unlocked phone exposes its contents. Data sent to the API is processed by a third party; Anthropic's current retention and training terms for API usage need checking before the first run.

**Backup:** with local-only storage, a lost or reset phone loses the diary. Regular export is the backup, and the app reminds the user to export: a monthly reminder (SK-9) and a context pill on Today after 7 days without an export, because free-account builds expire weekly.

## Architecture principles

The app serves one user today but is structured so it can later be extended, distributed or ported to another platform.

- **Ports and adapters:** core logic (logging, analysis requests, export) depends on small interfaces, and each external concern has its own adapter: LLM provider, key store, database, photo storage, barcode source, notifications and file sharing. Replacing Anthropic, Keychain or Open Food Facts touches one adapter.
- **Bring your own key:** every user supplies their own LLM key. No shared key and no server holds it, which keeps later distribution possible without a backend.
- **Portable data:** storage is a local database behind a repository interface, and the export schema is versioned and platform-neutral, so data can move to another app or platform.
- **Localization from day one:** all user-facing text lives in translation files. English ships first, Polish next.
- **Out of scope for v1:** App Store release, accounts, sync, a backend and medical-device claims. Distribution to others would need the paid Apple Developer Program, a privacy policy and a medical disclaimer.

**Constraints**

- Development happens on Ubuntu. A Mac is available only occasionally, so day-to-day work must not need one.
- Budget: free tooling where possible. Paid items so far are API usage and possibly the $99 per year Apple Developer Program.
- Free Apple Account builds expire after 7 days. The same account is reused; the app stops opening and must be rebuilt and reinstalled. This is accepted for the standalone phase. Moving to the paid program later (builds last up to a year) is possible, but it may require reinstalling the app, so export and import cover that move.
- EU alternative marketplaces and web distribution require notarized apps from Apple Developer Program members, so they are not a free route.
- No App Store release and no other users for now.

**Platform candidates (undecided)**

- **Expo (React Native), chosen for development:** daily coding on Linux with live reload on the real iPhone through Expo Go, free and with no Apple account. Expo Go is a development sandbox, not a standalone app: it needs the dev server running, supports only the SDK version of its App Store release (which lagged behind new SDKs in 2026), and keeps the app’s data inside Expo Go. A standalone build needs a Mac (free, 7-day expiry) or the paid program (cloud build, up to a year).
- **PWA:** no Apple involvement and no expiry, but weaker photo and key storage, awkward file export on iOS, and limited background behavior.
- **Flutter:** fast on Linux, but no equivalent of Expo Go for iOS, so iPhone problems surface late.
